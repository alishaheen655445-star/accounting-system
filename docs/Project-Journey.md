# 🧾 نظام المحاسبة الكامل — توثيق المشروع ورحلة التطوير
### Full-Stack Double-Entry Accounting System — University Final Project

> وثيقة شاملة بالعربي تشرح المشروع: التقنيات، البنية، قاعدة البيانات، المفاهيم المحاسبية، الميزات، ورحلة التطوير خطوة بخطوة. مفيدة لعرض التخرّج والمناقشة.

---

## ١) نبذة عن المشروع
نظام محاسبي إلكتروني متكامل مبني على مبدأ **القيد المزدوج (Double-Entry Bookkeeping)**: كل عملية مالية تُسجَّل في دفتر الأستاذ بجهتين — **جهة مدينة (Debit)** و**جهة دائنة (Credit)** — ومجموع المدين يساوي دائمًا مجموع الدائن.

**الوحدات (Screens) في النظام:**
- لوحة التحكم (Dashboard)
- دليل الحسابات (Chart of Accounts)
- العملاء (Customers)
- الموردون (Suppliers)
- المنتجات (Products)
- **المشتريات / إدخال المخزون (Purchases)**
- الفواتير والمبيعات (Invoices)
- الدفعات (Payments)
- قيود اليومية / دفتر الأستاذ (Journal)
- التقارير المالية (Reports)
- المستخدمون (Users)
- سجل التدقيق (Audit Log)

## ٣) البنية المعمارية (Architecture)
```
┌────────────────   HTTP/JSON    ┌──────────────────────────┐   SQL   ┌─────────┐
│   Frontend     │ ─────────────► │      Backend (API)       │ ──────► │  MySQL  │
│  (client/)     │ ◄───────────── │  Express :3000           │ ◄────── │ :3306   │
│ Vanilla JS+fetch│   JSON موحّد   │  Routes→Controllers→     │         │         │
└────────────────                │  Services→Models         │         └─────────┘
                                  └──────────────────────────┘
```

### ٣.١ طبقات الـ Backend (`server/`)
| المجلد | الدور |
|---|---|
| `server.js` | نقطة البداية: تركيب الـ middleware وتسجيل كل المسالك |
| `config/` | `db.js` (الاتصال) + `accounting.js` (أكواد الحسابات الافتراضية) |
| `routes/` | تعريف عناوين الـ API + الصلاحيات المطلوبة لكل مسار |
| `controllers/` | طبقة HTTP رقيقة: قراءة الطلب، نداء الـ service، ردّ JSON موحّد |
| `services/` | **عقل المشروع**: المنطق المالي، المعاملات، قواعد العمل |
| `models/` | كل استعلامات SQL (Parameterized) لكل جدول |
| `middleware/` | `auth` (JWT + أدوار)، `validate`، `errorHandler` مركزي |
| `validators/` | قواعد `express-validator` |
| `utils/` | `money` (حساب بالسنت الصحيح)، `jwt`، `i18n`، `ApiError`، `response`، `asyncHandler` |

### ٣.٢ بنية الـ Frontend (`client/`)
كل صفحة HTML تحمّل السكربتات بترتيب ثابت:
```
config → api → auth → ui → layout → crud → lookups → <منطق الصفحة>
```
| الملف | الدور |
|---|---|
| `api.js` | غلاف حول `fetch`: يضيف التوكن + رأس اللغة `X-App-Lang`، ويوحّد قراءة الرد |
| `auth.js` | حفظ الجلسة، حراسة الصفحات (`requireAuth`)، تسجيل الخروج |
| `ui.js` | الترجمة والاتجاه: `bi(en,ar,fa)`، `isRtl`، تنسيق المال `$`، الثيم |
| `layout.js` | القالب المشترك (القائمة الجانبية + الشريط العلوي) عبر `NAV` map |
| `crud.js` | أدوات مشتركة: `renderTable` و`openFormModal` |
| `lookups.js` | محمّلات مُخفّاة للقوائم (عملاء/منتجات/موردون/حسابات) |

## ٤) قاعدة البيانات (`database/`)
ملفان: `schema.sql` (الجداول) + `seed.sql` (بيانات البداية). التشغيل عبر `scripts/load-db.ps1`.

**أهم الجداول:**
`users` · `chart_of_accounts` (شجرة الحسابات) · `customers` · `suppliers` · `products` (+`stock_quantity`) · `invoices` + `invoice_items` · `purchases` + `purchase_items` · `journal_entries` + `journal_lines` · `audit_logs`.

**قواعد تصميم مهمة:**
- **المبالغ `DECIMAL(15,2)`** — ممنوع FLOAT/DOUBLE (دقة محاسبية).
- **مفاتيح أجنبية (FK)** مع قواعد حذف محسوبة:
  - `CASCADE` للبنود (invoice_items/purchase_items بلا أبوها ما بتعنشي شي).
  - `RESTRICT` لحماية السجل المالي (ما ينحذف عميل عنده فواتير).
  - `SET NULL` لربط الحسابات.
- **حذف ناعم (Soft Delete)** عبر `is_active` بدل الحذف الفعلي.
- **عمود `products.inventory_account_id`** يفرّق **البضاعة** (لها حساب مخزون → تُتَابَع بالكمية) عن **الخدمة** (NULL → تُباع بلا مخزون).

## ٥) المفاهيم المحاسبية والتقنية الأساسية
1. **القيد المزدوج** (`journalService`): القيد لا يمرّ إلا إذا: ≥٢ سطر، كل سطر مدين أو دائن (لا الاثنين)، **مجموع المدين = مجموع الدائن**، وكل حساب موجود وورقي (leaf).
2. **الدقة المالية** (`money.js`): كل الحسابات **بأعداد صحيحة (سنتات)** لتفادي أخطاء الفواصل العائمة (`0.1+0.2`)، والتحويل لـ"123.45" فقط عند العرض/التخزين.
3. **المعاملات الذرّية (Transactions):** الفاتورة + قيدها + حركة المخزون داخل `transaction` واحد (`beginTransaction/commit/rollback`) مع أقفال `SELECT ... FOR UPDATE` — إمّا تنجح كلها أو ترتد كلها.
4. **الصلاحيات (RBAC):** `admin` / `accountant` / `viewer`. القراءات لأي مستخدم مسجّل، الكتابة على البيانات لـ admin+accountant، إدارة المستخدمين والتدقيق لـ admin فقط.
5. **سجل التدقيق (Audit):** كل عملية كتابة تُسجَّل (`auditService`).
6. **توحيد الاستجابة:** كل الردود JSON بنفس الشكل (`success/message/data/meta`، والأخطاء `errors[]`).
7. **تعدد اللغات والاتجاه:** ثلاث لغات (EN/AR/FA) مع RTL، وأي عبارة غير مترجمة ترجع للإنكليزي تلقائيًا. العملة **دولار $** موحّدة على كل النظام.

## ٦) دورة العمل المالية (مثال سوبرماركت)
1. **شرائي من مورّد** (شاشة المشتريات) ← تزيد الكمية + قيد: `مدين المخزون / دائر ذمم المورد`.
2. **فاتورة مبيعات** (مسودة ← إصدار) ← عند الإصدار: `مدين ذمم العميل / دائر الإيرادات` + **تنقص الكمية** + `مدين تكلفة البضاعة المباعة (COGS) / دائر المخزون`.
3. **دفعة من عميل** ← `مدين الصندوق/البنك / دائر ذمم العميل`.
4. **التقارير** (ميزان مراجعة، قائمة دخل، مركز مالي) ← تتولّد من القيود.

> **مسودة vs مصدّرة:** المسودة ما بتأثر بدفتر الأستاذ ولا بالمخزون. التحويل لـ"مصدّرة" هو اللي بيقيد وبينقص الكمية.

## ٧) رحلة التطوير — شو عملنا خطوة بخطوة
> ملاحظة: المحادثة الأصلية كانت طويلة، فالتطبيق لخّص أقدمها. هذا ترتيب أهم المراحل يلي مرّينا فيها:

### المرحلة ١ — الأساس Full-Stack
- بناء هيكل المشروع (client/server/database)، الاتصال بـ MySQL، الـ middleware، الأخطاء الموحّدة.
- مصادقة JWT + bcrypt + أدوار (RBAC) + سجل تدقيق.
- CRUD كامل: دليل الحسابات، العملاء، الموردون، المنتجات، الفواتير، الدفعات، القيود، التقارير، المستخدمون.
- دقة مالية بالسنتات + قيد مزدوج متوازن.

### المرحلة ٢ — التوطين واللغات
- **إضافة الفارسي (FA)** كلغة ثالثة RTL مع fallback للإنكليزي.
- **توحيد العملة على الدولار $** على كل الشاشات (منتجات/حسابات/داشبورد/فواتير/دفعات) — تغيير رمز/تسمية فقط بلا أسعار صرف.
- توحيد اتجاه الواجهة (RTL/LTR) بمنطق CSS لا يتفرّع لكل لغة.

### المرحلة ٣ — إصلاح حسابات الذمم (قرار جذري)
- المشكلة: عميل جديد من الواجهة بلا `account_id` ← الفاتورة تفشل ("Customer has no receivable account").
- الحل: **إنشاء حساب فرعي تلقائي** لكل عميل (ذمم مدينة AR تحت 1300) وكل مورد (ذمم دائنة AP تحت 2100) داخل نفس المعاملة، + سكربت `backfillPartyAccounts.js` للأقدم.

### المرحلة ٤ — تقييد طرق الدفع
- الدفعات صارت **نقدًا (Cash) وبطاقة (Card)** فقط (شيلنا بنك/شيك).

### المرحلة ٥ — دورة حياة الفاتورة
- إضافة **إصدار (Issue)** للمسودة (بينقلها لمصدّرة + يقيد + ينقص المخزون) و**حذف (Delete)** للمسودة فقط.
- حماية: الفاتورة المصدّرة ما تنحذف (لازم تُلغى)، والمسودة ما تنقيد.

### المرحلة ٦ — المخزون (المستوى الكامل B)
- عمود `stock_quantity` + جداول `purchases`/`purchase_items` + وحدة مشتريات كاملة (API + شاشة).
- الشرائي يزيد الكمية ويقيد `مدين المخزون / دائر AP` ويحدّث تكلفة المنتج (last-cost).
- البيع ينقص الكمية ويقيد `مدين COGS / دائر المخزون`، و**يمنع البيع أكبر من المتوفر**.
- ملف `database/migrations/001_inventory.sql` (idempotent) للقواعد الموجودة.

### المرحلة ٧ — إصلاح الخدمات vs البضاعة
- الخطأ: فاتورة فيها "خدمة تركيب" انرفضت ("Insufficient stock"). السبب: النظام كان بيعامل كل منتج كبضاعة.
- الحل: **المنتج اللي بلا حساب مخزون = خدمة** → تُباع بلا كمية ولا COGS، والشرائي يرفض تخزين خدمة.

### المرحلة ٨ — إصلاح توليد الأرقام
- الخطأ القديم: رقم الفاتورة كان `COUNT+1` ← تصادم (409) لما الحذف يسيّب فجوات بالتسلسل.
- الحل: `MAX(الرقم التسلسلي)+1` للفواتير والمشتريات (آمن من الفجوات).

## ٨) قرارات هندسية وأخطاء تعلّمناها
- **الحسابات داخل معاملة واحدة** — لا فاتورة بلا قيدها ولا العكس.
- **السنتات الصحيحة بدل float** — أساس الدقة المحاسبية.
- **الخادم هو مصدر الحقيقة للسعر** — سعر الوحدة بيجي من كتالوج المنتج، مش من العميل.
- **الفرق بين البضاعة والخدمة** عبر `inventory_account_id` (لا خلط بالمخزون).
- **توليد الأرقام على MAX مش COUNT** (الفجوات بتسبّب تصادم).
- **UTF-8 عند استيراد SQL بالعربي** عبر `Start-Process -RedirectStandardInput` (الـ pipe بيحوّل العربية لـ"؟").

## ٩) كيف تشغّل المشروع محليًا
```bash
# 1) قاعدة البيانات (XAMPP MySQL على :3306)
npm run db:load          # يشغّل schema.sql ثم seed.sql

# 2) الـ API على :3000
npm start                # أو: npm run dev (nodemon)

# 3) الواجهة على :5500 (خادم ملفات ثابتة)
npx http-server client -p 5500 -c-1
```
- **الدخول:** `admin / Admin@123` (و `accountant` / `viewer`).
- **البيئة:** ملف `.env` يحوي بيانات الاتصال و`JWT_SECRET` (غير مربوط بـ git).

- ورّي **المخزون**: شرائي يزيد، بيع ينقص، منع العجز، وCOGS.
- ورّي **تعدد اللغات + RTL** كميزة UI متقدّمة.
